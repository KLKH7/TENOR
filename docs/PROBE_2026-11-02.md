# Live probe of Granola's MCP (2026-11-02)

The probe was run from Claude Code against the official MCP (`https://mcp.granola.ai/mcp`, OAuth). It was read-only: we called no write tools. It ran on the author's own account, which is on the **Plus** plan, with one workspace, scopes `personal` + `public`, and **4 meetings in total** (Oct 16–30, 2026). Meeting content is deliberately not reproduced here; this file records only how the MCP behaves.

## 1. The MCP has changed a lot since the brief, and since the docs we read on 2026-10-29

| Observation | Implication |
|---|---|
| `query_granola_meetings` is now an **agent** that "searches and reads the user's notes". It returns structured, cited answers, such as a commitments table with owner, due date and "later status". | The "looks at the 20 most relevant meetings" description (Platformer, July 2026) is **out of date**. The baseline Concentrate must beat is an agentic retriever, not naive top-k. |
| New retrieval tools: `search_meetings` (keyword, participant, date; cursor pagination) and `search_transcripts` (ranked 240-char passages with `chunk_id`s and a `transcript_version`, read via `get_meeting_transcript(chunk_ids=...)`). | Granola already exposes chunked, citable transcript retrieval. |
| **Write tools exist:** `update_private_notes`, `create_folder`, `update_folder`, `add_note_to_folder`, `remove_note_from_folder`, `generate_summary`, `list_templates`, `give_feedback`. | The MCP is no longer read-only. Not exercised (side effects). |
| Tool descriptions carry detailed **guardrails for agents**: verify against transcripts, don't infer ownership from a shared heading, "dated plans do not establish current progress", resolve "this week" relative to the meeting date. | Granola is addressing several of Concentrate's target problems through prompting. |
| Every answer starts with a `transcript_note`: the answer "comes from meeting notes, which are condensed overviews… call search_transcripts… before answering". | Answers are summary-first. Exact details need extra tool round-trips, which is a latency and token cost on every query. |

## 2. Transcript format (the real thing vs. our synthetic model)

- Each passage has a `speaker` label of either `Microphone` or `System audio`, and **system audio is often attributed to a named person**: `System audio (<Full Name>)`. Some system-audio passages stay unlabeled.
  - **Our synthetic data assumes Me/Them only, with no names. Reality is better than that.** The public REST API's `speaker.name` ("only present when identified") matches this. Fixtures should include partially named system-audio speakers.
- A `recording_context` block names the **recorder** (the note owner) and says that "unidentified speech and room labels can contain multiple voices". It also reports `microphone_sharing: unknown`.
- Utterances are **very short and fragmentary** (often 1–5 words), more so than our synthetic segments.
- ASR errors match our noise model: misheard names and words, and dropped or garbled function words.
- `search_transcripts` passages have **no speaker attribution** (240-character windows). Attributing a quote needs a second `get_meeting_transcript` call.

## 3. Failure modes observed (where Concentrate could still add value)

1. **Cross-meeting entity resolution miss (confirmed).** Asked "who is <teammate>, and which meetings did they appear in?", Granola said **one** meeting. The person is also addressed by name in an earlier meeting's transcript, and appears in that meeting's own AI summary, where they're assigned a next step. In that earlier meeting the attendee list shows people only as email handles (e.g. university UNIs), so the name was never linked to an attendee. This is exactly the problem Concentrate's entity linking targets.
2. **"Unidentified speaker" owners in an in-person meeting.** In the in-person board meeting, several commitments came back with owner **"Unidentified speaker"**, because everyone was on one microphone. Our synthetic in-person meetings model this failure directly.
3. **Status tracking is conservative but shallow.** Most items were marked "no later evidence". That's honest, but with only summaries as input it can't separate *dropped* from *not discussed*.
4. **Latency.** The tool's own description calls `query_granola_meetings` "slow". It runs an agent per question, whereas a precomputed memory answers from a store.

## 4. Unofficial internal API (reverse-engineered) — not used

Sources: Joseph Thacker (2025-05-08); getprobo/reverse-engineering-granola-api (Nov 2025, **archived 2026-02-05**, and its README calls itself obsolete now that the official API exists).

- `POST https://api.granola.ai/v2/get-documents` returns notes as ProseMirror JSON (`last_viewed_panel`).
- `POST /v1/get-document-transcript` returns utterances with `source` (microphone|system), `start_timestamp`, `end_timestamp` and a per-utterance **`confidence`** score. The public API doesn't expose confidence.
- Auth works by extracting WorkOS tokens from the desktop app's local `supabase.json`, and refresh tokens are single-use.

**Decision: don't build on it.** It requires extracting local credentials, it's undocumented and pinned to a client version, it's superseded by the official API and MCP, and building on Granola's private API is the wrong signal in a pitch to Granola.

## 5. Consequences for the project

- **Reposition the thesis.** The comparison isn't "Concentrate vs dumb top-k"; it's **precomputed, entity-resolved, time-aware memory vs per-query agentic retrieval over summaries and transcripts**. The claims worth measuring are:
  - accuracy on entity, temporal and status questions;
  - tokens and latency per query, where precomputation should win clearly;
  - consistency across meetings (the entity miss above).
- **Baselines (Phase 3)** should include an *agentic* retriever that mirrors the current MCP (search, then read the summary, then read transcript chunks), not only top-k stuffing.
- **Fidelity fixes to the synthetic data:** named system-audio speakers in some meetings, shorter and more fragmented utterances, and attendee lists that show email handles instead of names.
- **A real-data path:** this account is on Plus, so the public REST API (Business/Enterprise only) isn't available, but the MCP is. A `GranolaMCPSource` would let Concentrate ingest real notes through the same `Source` protocol.
- **Scale caveat:** 4 meetings can't test retrieval at scale. Any real-data claims need more meetings, and the synthetic benchmark remains the controlled test.
